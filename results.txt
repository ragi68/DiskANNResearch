CLUSTER GRAPH BOUNDARY EDGES vs VAMANA - RESULTS (2026-09-30)
==============================================================

Shared cluster graph base (both ideas):
  - k-means with C = sqrt(n) clusters (141 at n = 20000)
  - slow preprocessing inside each cluster (RobustPruning against the whole cluster), pruneR = 70
  - hub node -> every cluster medoid; search = hub -> nearest medoid -> greedy search
  - totalR = 125 caps out-degree after boundary edges are added


IDEA 1: RANDOM POOL EDGES  (AddBoundaryEdges, adjacencyEdges.cpp)
-----------------------------------------------------------------
  1. Each point of cluster i joins the pool "i facing j" for its 14 nearest foreign medoids
     (10% of clusters), scored by margin d(x, m_j) - d(x, m_i).
  2. Each pool keeps its 40 smallest-margin points.
  3. Clusters are adjacent if either side has a pool facing the other.
  4. For each adjacent pair, both directions: 25 edges between uniformly random pool points.
  Params: edgesPerPair = 25, poolSize = 40, numAdjacentClusters = 14.


IDEA 2: RANKED EDGES  (AddBoundaryEdgesRanked, adjacencyEdges.cpp)
------------------------------------------------------------------
  1. Every vertex x computes its bisector distance to each foreign cluster j:
       h_j = (d(x,m_j)^2 - d(x,m_i)^2) / (2 * d(m_i,m_j))
     and keeps the clustersPerVertex clusters with smallest h.
  2. In each, takes the candperCluster = 50 points nearest to x.
  3. Draws edgesPerCluster targets with P(rank r) ~ 1/r (Kleinberg-style rank weighting).
  4. (Added after the runs below, not yet measured) reverse edge y -> x for each x -> y.
  Params: clustersPerVertex = 14, edgesPerCluster = 3  ->  up to 42 cross edges per vertex.

COMPARABILITY NOTES
-------------------
  - Same across 128-D runs: data, queries, alpha = 1.2, search L, recall = true top-10 found in visited set.
  - NOT same: degree. Cluster graphs may use up to 125 edges/node vs Vamana's 70.
  - Vamana query time uses the rewritten GreedySearch (cached distances, hash sets);
    clusterGreedySearch already worked that way, so query times are comparable.
  - Vamana build is still inflated by RobustPruning recomputing distances inside its sort comparator.


TAKEAWAYS
---------
  - Build: cluster graphs build ~25-30x faster than Vamana (no back-edge re-pruning, candidate sets ~sqrt(n)).
  - Recall: ranked edges beat random pools (0.523 -> 0.743) but trail Vamana (0.937), despite more edges.
  - Coverage matters most: ranked edges into 1-2 clusters gave 0.275; spreading over 14 clusters gave 0.743.
  - Query cost: Vamana ~26% cheaper per query than idea 2 (fewer edges per node).

  Next: multi-medoid search entry, alpha-diversified targets per cluster, degree-matched comparison,
  and re-run idea 2 with reverse edges.

UPDATE (2026-10-14 / 2026-10-15): RE-RUNS, BACKBONE, PATCH GRAPH
==============================================================

Changes since the runs above:
  - Search entry is now a coarse layer over the medoids (topLevelEdges, medoidR = 24;
    coarseGreedySearch, p = 1) instead of the hub node.
  - Idea 2 now includes the reverse edges noted above.
  - New edge mode, IDEA 3: BACKBONE (BackBoneGraph, adjacencyEdges.cpp): the top
    boundaryProportion of each cluster, scored by the length of the mean unit direction
    to its in-cluster neighbours (findGlobalBoundaryNodes), is RobustPruned against the
    boundary nodes of every other cluster; edges merged after in-cluster edges, cap totalR.
  - New graph type, PATCH GRAPH (PatchGraph::PatchANN, DiskANN-Patch/patchANN.cpp): see below.

PATCH GRAPH  (PatchGraph::PatchANN, DiskANN-Patch/patchANN.cpp; -patch)
----------------------------------------------------------------------
  1. Patches of s = ceil(sqrt(n)) distinct vertices (142 at n = 20000), drawn uniformly
     from a pool; a vertex leaves the pool once it is in k patches.
  2. At most k * s patches; with spare slots (k * s^2 > k * n) every vertex ends in exactly
     k patches. (Perfect-square n has no spare slots: a few vertices end one short of k.)
  3. Slow preprocessing inside each patch: RobustPruning against the whole patch,
     alpha = 1.2, R = 70. A vertex in several patches keeps its earlier edges as candidates.
  4. Search: classic GreedySearch from the dataset medoid (same as the Vamana tests).

RESULTS: 128-D, n = 20000 uniform [0,1000], 100 queries, search L = 125, seed 42
  k    Patches   Build      Recall@10  Worst q  Avg query  Avg out-degree
  2      283      142 s     0.574      0.3      5.04 ms    70.0
  3      424      291 s     0.722      0.3      6.43 ms    70.0
  4      565      379 s     0.766      0.4      5.29 ms    70.0
  8     1131      718 s     0.829      0.5      6.55 ms    70.0
  12    1693     1429 s     0.864      0.5      5.35 ms    70.0      (12 ~ n^(1/4))

  - Every vertex was in exactly k patches at every k (test check passed).
  - Diminishing returns: k 2 -> 4 gives +0.19 recall, k 4 -> 12 gives +0.10.
  - Build grows faster than linearly in k once out-lists are full (more candidates per prune).
  - Two points share a patch with probability ~ k / sqrt(n) (1.4% at k = 2, 8.5% at k = 12),
    yet recall is high: likely because distances concentrate in 128-D uniform data, so
    in-patch neighbours are still useful steps for greedy search. Not verified.
